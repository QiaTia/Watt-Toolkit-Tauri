# 终端（命令行 / CLI）流量劫持能力分析：原版 vs 本版

> 触发问题：**原版 Watt Toolkit 能劫持并加速「终端」的流量，本版(Migrated Tauri 版)不可以。**
> 分析日期：2026-10-19
> 证据来源：本仓源码 + `doc/task.md`、`doc/迁移一致性审计.md`（对原版 C# `BD.WTTS.Client.Plugins.Accelerator*` 逐文件审计的结论）。
> ⚠️ 未直接读取原版 C# 仓库源码（本机无该仓库，且当前网络对 github.com 直连 TLS 受限），原版机制结论引自上述审计文档，已标注出处。

---

## 一、结论速览

| 判定 | 结论 |
|---|---|
| 是一致性 bug 吗？ | **不是**。属于**有意的能力裁剪**（`doc/task.md:13/215` 明确「不迁移 WinDivert/DNSIntercept 模式」与「VPN(tun2socks)」），但迁移后**没有提供任何等价的终端侧接入面** |
| 直接原因 | 本版所有模式都依赖「**应用自觉**」：Hosts 靠系统解析器、System/PAC 靠 WinINET。终端类工具既不读 WinINET 系统代理，也不看 PAC → 在 System/PAC/ProxyOnly 下**根本不会被劫持** |
| 次生原因 | 即使 Hosts 模式劫持成功，CLI 工具自带 CA bundle → **TLS 校验失败**，表现为「连不上」而非「被加速」 |
| 产品层缺口 | 无环境变量注入、无 WinHTTP 设置、无 CLI 证书注入、SOCKS5(8868) 已实现但无「终端怎么用」的指引 |
| 解决路径 | 方案 1（环境变量 + CA 注入，低成本，立竿见影）→ 方案 3（本机 DNS 拦截，零驱动）→ 方案 4（TUN/VPN，终极） |

## 二、核心机制：三个接入面的覆盖范围不同

加速引擎能「劫持」什么流量，完全取决于它把**接入面**设在网络栈的哪一层。本版现有的四种模式，本质只有两种接入面：

| 接入面 | 实现 | 谁遵守它 | 终端 / CLI 是否覆盖 |
|---|---|---|---|
| **hosts 文件**（Hosts 模式） | `engine.rs:500-516` 写 `域名 → 127.0.0.1` | 一切**走系统 DNS 解析**的进程（几乎所有进程，含 git/curl/npm/python 默认路径） | ✅ 覆盖（但见根因 B 的信任问题） |
| **WinINET 系统代理**（System 模式） | `system_proxy.rs:44-139` 写 `HKCU\...\Internet Settings`（ProxyEnable/ProxyServer/ProxyOverride） | **只**遵守 WinINET 的进程：IE/Edge/Chrome、部分 .NET/Office/Inet 系组件 | ❌ **不覆盖**：git / curl / npm / pip / python / ssh / go 都不读这个键 |
| **WinINET PAC**（PAC 模式） | `system_proxy.rs:142+` 写 `AutoConfigURL` | 同上（PAC 本来就是 WinINET 的一个特性） | ❌ 同上 |
| **裸监听**（ProxyOnly / SOCKS5 8868） | `listener.rs:228+`、`commands/engine.rs:123` | 不写任何系统设置，需**手动**配置客户端 | ⚠️ 手动可用（如 `ALL_PROXY=socks5://127.0.0.1:8868`） |
| **DNS 包拦截**（原版 `DNSIntercept`） | 原版用 **WinDivert** 抓包（`迁移一致性审计.md:103`、`task.md:9`） | 全机所有发起 DNS 查询的进程，**进程无关**，且不受 hosts 写入权限/hosts 缓存影响 | ✅ 覆盖，比 hosts 更"硬" |
| **虚拟网卡**（原版 `VPN`，tun2socks） | `task.md:215`（Android/VPN(tun2socks)） | 全机 TCP/UDP 流量（连硬编码 IP、非 443 端口也接管） | ✅ 完全覆盖 |

**本版实施现状**：`ProxyMode` 只剩 `Hosts / System / Pac / ProxyOnly`（`ui/src/types/ipc.ts:68`），旧版 `DNSIntercept → Hosts`、`VPN → 不支持`（`crates/watt-config/src/settings.rs:22-32`、`migrate.rs:105-115`）。

> 一句话：原版有两个「从内核/网卡层面强行接管」的接入面（DNSIntercept、VPN），本版全部没有，只剩下「应用自己愿意配合」的接入面。**终端类工具恰恰是最不配合的那一类。**

## 三、三层根因

### 根因 A｜机制层：原版独有的两个系统级接入面未迁移

- 原版 `ProxyMode` 枚举：`DNSIntercept(0) / Hosts(1) / System(2) / VPN(3) / ProxyOnly(4) / PAC(5)`（`task.md:512/737/789`）
- 本版保留 4 个，**DNSIntercept 与 VPN 被显式排除**（`task.md:13`、`task.md:215`）
- 后果：原版可以把「不读 WinINET、甚至自建 DNS 客户端」的进程的流量拉进加速链路；本版做不到。

### 根因 B｜信任层：劫持成功 ≠ 加速成功（CLI 自带 CA bundle）

MITM 要求客户端信任自签 CA。本版 CA 装在 **CurrentUser\Root**（`crates/watt-cert/src/trust.rs:117`，`CertOpenSystemStoreA(0, "ROOT")`）。Windows 证书链构建会合并「用户根 + 机器根」，所以**走 Schannel 的进程**（IE/Edge、`git` 默认 schannel 后端、.NET）一般能通过；但 CLI 工具大多**自带根证书包**，完全无视 Windows 证书库：

| 工具 | 信任来源 | 典型报错 |
|---|---|---|
| `curl`（Windows 自带/多数发行版） | 自带 `cacert.pem`（可 `--cacert` / `CURL_CA_BUNDLE` 覆盖） | `SSL certificate problem: unable to get local issuer certificate`（exit 60） |
| `git`（OpenSSL 后端） | 自带 bundle（`http.sslCAInfo` 可覆盖） | `SSL certificate problem` |
| `node` / `npm` / `pnpm` | 内置根证书（可用 `NODE_EXTRA_CA_CERTS` 追加） | `UNABLE_TO_VERIFY_LEAF_SIGNATURE` |
| `python` / `pip` | `certifi`（可用 `REQUESTS_CA_BUNDLE` / `SSL_CERT_FILE`） | `CERTIFICATE_VERIFY_FAILED` |
| `go` | 内置 | `x509: certificate signed by unknown authority` |

→ 现象：「终端里访问加速域名**报证书错/连接被重置**」，用户感知就是「终端流量没被加速」。注意这与原版差异需实测确认：本仓审计文档**未见**原版有任何「CLI 证书注入」机制（见第八节待确认项）。

### 根因 C｜产品/接线层：本版没有任何终端侧入口

| 缺口 | 证据 |
|---|---|
| 无环境变量注入（`HTTP_PROXY/HTTPS_PROXY/ALL_PROXY/NO_PROXY`） | 全仓 grep 无写入逻辑，仅在文档中出现 |
| 无 WinHTTP 代理设置（`netsh winhttp` / WinHttp API） | 全仓 grep 无 `winhttp` |
| SOCKS5 已实现但无指引 | `listener.rs:228+`（8868）已接线（`SettingsPage.vue:217`、`AcceleratorPage.vue:285`），但 UI 文案未告知终端如何配置 |
| UI 文案有误导 | `ui/src/locales/zh-Hans.ts:75` 系统代理 desc 写「**全局生效**」——实际只对 WinINET 进程生效，终端不在其内 |
| 脚本子系统已被移除 | `commands/engine.rs:132`（`scripts: Vec::new()`），与原版差距另见 `迁移一致性审计.md:98` |

## 四、诊断树：先判定你落在哪一层

按顺序执行（PowerShell）：

```powershell
# 1. 接入面是否符合当前模式（Hosts 应听 443；System/PAC/ProxyOnly 应听 26501）
netstat -ano | findstr "LISTENING" | findstr ":443 :26501"

# 2. 系统代理面是否生效（=1 → WinINET 面开着，注意 DNSIntercept/终端无关）
reg query "HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings" /v ProxyEnable

# 3. hosts 面是否生效（返回 127.0.0.1 才算劫持成功）
Resolve-DnsName github.com

# 4. 终端真实路径对比（--noproxy '*' 强制忽略环境变量/系统代理）
curl.exe -v --noproxy '*' https://github.com/ -o NUL

# 5. 正向代理面自检
curl.exe -x http://127.0.0.1:26501 -v https://github.com/ -o NUL

# 6. WinHTTP 面（当前必然为 direct）
netsh winhttp show proxy

# 7. 工具自身是否配了代理
npm config get proxy; npm config get https-proxy; git config --get http.proxy
```

判定表：

| 现象 | 归属 | 对应方案 |
|---|---|---|
| `Resolve-DnsName` 返回**真实 IP**，终端直连且 200（未被加速） | System/PAC/ProxyOnly 模式不覆盖 CLI | 方案 1 / 2 / 3 |
| `Resolve-DnsName` 返回 **127.0.0.1**，但 curl/git 报证书或连接错 | 劫持成功、**信任失败** | 方案 1 的 CA 注入部分 |
| `Resolve-DnsName` 返回 127.0.0.1 且 **443 无监听** | 接入面不一致（已知铁律，见 `doc/MEMORY.md`） | 先修接入面，再谈终端 |
| 终端访问的是**未勾选/未在分组内**的域名 | 规则问题，非终端问题 | 勾选对应加速分组 |
| 需要覆盖「自建 DNS/DoH 客户端、硬编码 IP、非 HTTP 协议」 | 原版 DNSIntercept/VPN 才具备 | 方案 3 / 方案 4 |

## 五、解决方案（按成本由低到高）

### 方案 1｜终端代理环境变量 + CA 一键注入（低成本，建议先做）

**覆盖**：git / curl / npm / pnpm / pip / python / go 等一切「读环境变量」的工具（含 `-x` 无效的空壳环境）。

**做法**（用户级环境变量，不写 HKLM、不需要管理员）：
- `HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY` = `http://127.0.0.1:26501`（或 `socks5://127.0.0.1:8868`，复用已实现的 SOCKS5 入站）
- `NO_PROXY` = 复用 `system_proxy.rs:11 no_proxy_host_names()`（内网段 + 官方 API），避免加速服务自身被代理
- CA 注入：`NODE_EXTRA_CA_CERTS` / `REQUESTS_CA_BUNDLE` / `SSL_CERT_FILE` / `CURL_CA_BUNDLE` / `GIT_SSL_CAINFO` 指向 `{data_dir}/Certificates/ca.cert.pem`
- 写完广播 `WM_SETTINGCHANGE`，并提示「已打开的终端需重开或重载会话」

**落点**：
- 新增 `crates/watt-core/src/terminal_proxy.rs`（set / clear 幂等 + 单测）
- `src-tauri/src/commands/` 增命令，与 `engine_start/engine_stop` 联动（**必须与引擎同生命周期清理**，遵守「接入面与运行态一致」铁律，并纳入 `cleanup_orphans` 兜底）
- UI：加速页加「终端代理（可选）」开关 + 证书说明
- 兼容 `ProxyMode::System/Pac`（那时 26501 在监听）；Hosts 模式无 26501 在听 → 该开关应只在「正向代理在监听」时可用，或 Hosts 模式下改为给终端提供 CA 注入指引（配合根因 B）

**风险**：全局环境变量影响所有新启动进程，可能与其他代理软件冲突 → 只允许用户显式开启 + 退出必清。

### 方案 2｜补 WinHTTP 系统代理（中成本，覆盖面有限）

**做法**：`netsh winhttp set proxy 127.0.0.1:26501 "<bypass>"`（需管理员）或调用 `WinHttpSetDefaultProxyConfiguration`。
**覆盖**：仅使用 WinHTTP 组件的进程/服务（Windows 原生组件、部分 CLI）。
**局限**：现代 CLI 基本自带 HTTP 栈（Go/Rust/Node 都读环境变量而非 WinHTTP），收益不如方案 1 → 建议作为方案 1 的补充而非替代。

### 方案 3｜本机 DNS 拦截（中成本，零驱动，最接近原版 DNSIntercept 的意图）

**思路**：不引入 WinDivert 驱动，用「本机 DNS 服务」达成同等效果——
1. 在 `127.0.0.1:53` 起 DNS 服务（`watt-dns` 已有 hickory-resolver 基础）
2. 命中加速规则的域名应答 `127.0.0.1`；其余转发 `master_dns`
3. 把系统 DNS 指向 `127.0.0.1`（`Set-DnsClientServerAddress`，需管理员）或仅让引擎内部使用

**覆盖**：所有走系统 DNS 的进程（含终端），且**不受 hosts 文件写入权限与 hosts 缓存影响**。
**不覆盖**：应用内自建 DoH（如浏览器 DoH、`dns.google` 硬编码）。
**风险**：改系统 DNS 影响全局网络（断网风险），必须与引擎启停严格联动清理；53 端口可能被占用（可复用 `port_diag` 诊断）。
**决策建议**：若严格对齐原版 WinDivert 行为需引入驱动（管理员 + 签名 + 杀软误报），本仓已明确回避该路线 → 建议采用本节这种「用户态 DNS 拦截」等价实现。

### 方案 4｜VPN / TUN 模式（高成本，终极方案）

**做法**：`wintun`（WireGuard 官方用户态驱动，无需自签名驱动安装）+ `tun` crate + 用户态 TCP/IP 栈（smoltcp / tun2socks 类实现）。
**覆盖**：真·全流量（硬编码 IP、任意端口、非 HTTP 协议全接管），终端自然在内。
**风险**：需管理员、接管路由表（断网风险极高）、与其它 VPN/加速器冲突、杀软误报；工作量最大。
**定位**：除非产品目标包含「全协议/游戏类加速」，不建议作为首选。

## 六、方案对比

| # | 方案 | 覆盖终端 | 覆盖非 HTTP/硬编码 IP | 需管理员/驱动 | 成本 | 与现有代码复用度 |
|---|---|---|---|---|---|---|
| 1 | 环境变量 + CA 注入 | ✅ 读环境变量的工具 | ❌ | 否 | 低 | 高（复用 26501/8868 + `no_proxy_host_names`） |
| 2 | WinHTTP | ⚠️ 仅 WinHTTP 组件 | ❌ | 是（netsh） | 中 | 中 |
| 3 | 本机 DNS 拦截 | ✅ 走系统 DNS 的进程 | ❌ | 是（改系统 DNS） | 中 | 中（复用 `watt-dns`、`hosts`/规则匹配） |
| 4 | TUN / VPN | ✅ 全部 | ✅ | 是（驱动） | 高 | 低（需新栈） |

## 七、建议落地顺序与验收

1. **先按第四节判定属于哪一层**（多数用户场景 = 根因 A/B → 方案 1 即可解决）
2. 落地方案 1：新增 `crates/watt-core/tests/diag_terminal_env.rs`（不依赖外网：断言环境变量写入/清理幂等 + 本地 mock 上游，`curl.exe`/`node` 经 26501 返回 200 且证书校验通过）
3. 方案 1 稳定后落地方案 3：新增 `diag_dns_intercept.rs`（注入临时 DNS 端口，断言「加速域名 → 127.0.0.1 / 非加速域名转发上游」）
4. 方案 4 仅在明确需要「全协议接管」时立项（真机验收：`curl.exe --noproxy '*' https://github.com` 命中原版加速链路）

## 八、待确认项与风险

1. **原版机制结论的取证强度**：本机无原版 C# 仓库、网络受限，WinDivert/DNSIntercept 与 VPN(tun2socks) 的存在依据来自本仓审计文档（`task.md:9/215`、`迁移一致性审计.md:103`），未逐行读原版源码。若需 100% 确认，建议在有网络的环境核对原版 `ProxyService.Operate.cs`、`WinDivert` 相关文件。
2. **原版是否额外处理过 CLI 证书信任**：本仓审计文档未见相关条目。若原版确实在 Hosts 模式下能让 `curl`/`git` 正常访问加速域名，则差异点应重新定位到「信任层」而非「机制层」——需要一次对照实测（同一终端命令、同一域名、原版 vs 本版）。
3. **「终端」的边界**：本文按「终端内运行的命令行工具」理解。若你指的是「**原版 VPN/DNS 拦截模式**那种系统级接管」，请直接对应方案 3/4；若指某个具体工具（如某个 IDE/客户端/自研脚本）的流量，请给出具体命令与报错，可按第四节判定表精确定位到工具级方案。
